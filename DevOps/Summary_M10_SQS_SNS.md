## 1. ภาพรวมการประมวลผลแบบอะซิงโครนัสและประเภทบริการส่งข้อความ (Messaging Services)

- **Asynchronous Processing:** การแยกส่วนประกอบของระบบ (Decoupling) ให้ทำงานเป็นอิสระต่อกันโดยไม่ต้องรอผลตอบกลับทันที ช่วยลดความพึ่งพาซึ่งกันและกัน (Loose Coupling) ป้องกันปัญหาคอขวด และเพิ่มความพร้อมใช้งานของระบบโดยรวม
- **3 เสาหลักของบริการส่งข้อความบน AWS (สไลด์หน้า 10 & 62):**
  1. **Message Queues (Amazon SQS):** การสื่อสารแบบ 1 ต่อ 1 (Point-to-Point) ข้อความถูกเก็บในคิว รอให้ Consumer ตัวใดตัวหนึ่งดึงไปประมวลผลและลบทิ้ง
  2. **Pub/Sub Messaging (Amazon SNS):** การสื่อสารแบบ 1 ต่อ N หรือ หลายต่อหลาย (Fanout / Broadcast) ส่งข้อความครั้งเดียว กระจายสำเนาไปยังผู้รับทุกคนที่ Subscribe ไว้
  3. **Data Streams (Amazon Kinesis):** สตรีมข้อมูลต่อเนื่องขนาดมหาศาลแบบเรียลไทม์ ข้อมูลไม่ถูกลบเมื่ออ่านแล้ว แต่จะมีตัวชี้ (Pointers / Shard Iterators) ให้หลาย Consumer อ่านวนซ้ำได้

## 2. Amazon SQS (Simple Queue Service)

บริการคิวข้อความแบบ Fully Managed ไม่จำกัดปริมาณข้อความ ปลอดภัย และมีค่าบริการตามการใช้งานจริง:

### 2.1 เปรียบเทียบประเภทคิว: Standard Queue vs FIFO Queue

| คุณสมบัติ | Standard Queue (ค่าเริ่มต้น) | FIFO Queue (First-In, First-Out) |
| :--- | :--- | :--- |
| **การเรียงลำดับ (Ordering)** | **Best-effort ordering** (ลำดับอาจคลาดเคลื่อนได้ ไม่การันตี 100%) | **First-In, First-Out 100%** (ข้อความเข้าก่อนต้องออกก่อนตามลำดับ) |
| **การส่งมอบ (Delivery)** | **At-least-once delivery** (อาจมีข้อความซ้ำส่งมาได้มากกว่า 1 ครั้ง) | **Exactly-once processing** (รับประกันไม่ส่งซ้ำเด็ดขาด) |
| **Throughput ขีดจำกัด** | **เกือบไร้ขีดจำกัด (Nearly unlimited)** | 300 ธุรกรรม/วินาที (หรือ 3,000 ธุรกรรม/วินาที เมื่อทำ Batching) |
| **การตั้งชื่อคิว** | ตั้งชื่ออะไรก็ได้ | **ต้องลงท้ายด้วย `.fifo` เสมอ** (เช่น `orders.fifo`) |
| **พารามิเตอร์บังคับ** | ไม่มี | ต้องส่ง `MessageGroupId` และ `MessageDeduplicationId` |
| **Use Cases ที่เหมาะสม** | งานถอดรหัสวิดีโอ, งานปรับขนาดรูป, งานที่ไม่สนลำดับ | **ธุรกรรมการเงิน (ฝาก-ถอนธนาคาร)**, จองตั๋ว, สมัครสมาชิก |

### 2.2 วงจรชีวิตของข้อความ (Message Lifecycle - จากไดอะแกรมหน้า 20 & 23)
1. **`SendMessage`:** Producer ส่งข้อความเข้าคิว (ขนาดสูงสุด **256 KB ต่อข้อความ**) SQS จะคัดลอกข้อมูลกระจายข้ามหลายเซิร์ฟเวอร์แบบ Redundant
2. **`ReceiveMessage` & Visibility Timeout:**
   - เมื่อ Consumer สั่งดึงข้อความ SQS จะส่งมอบข้อความพร้อมกับ **`ReceiptHandle`**
   - SQS จะเริ่มจับเวลา **Visibility Timeout (ค่าเริ่มต้น 30 วินาที, ปรับได้ 0 วินาที ถึง 12 ชั่วโมง)**
   - ในช่วงเวลานี้ **ข้อความจะถูกซ่อนให้มองไม่เห็น** จาก Consumer ตัวอื่น เพื่อป้องกันไม่ให้มีใครนำงานชิ้นเดิมไปทำซ้ำ
3. **`DeleteMessage`:**
   - เมื่อ Consumer ประมวลผลงานเสร็จ **ต้องส่งคำสั่ง `DeleteMessage` โดยแนบ `ReceiptHandle` กลับมาลบข้อความออกจากคิวด้วยตนเองเสมอ**
   - ⚠️ **หาก Consumer ตายหรือล้มเหลวก่อนลบ:** เมื่อ Visibility Timeout หมดลง ข้อความจะ **กลับมาปรากฏในคิวอีกครั้งโดยอัตโนมัติ** เพื่อให้ Consumer ตัวอื่นดึงไปทำต่อ

### 2.3 Short Polling vs Long Polling (การดึงข้อมูลจากคิว)
- **Short Polling (`WaitTimeSeconds = 0`):** SQS จะสุ่มถามเพียงบางเซิร์ฟเวอร์ในคลัสเตอร์ และตอบกลับทันที แม้ในคิวจะมีข้อความอยู่แต่อาจได้ผลลัพธ์ว่างเปล่า (Empty Receive) ทำให้เปลืองคำสั่ง API และสิ้นเปลืองต้นทุน
- **Long Polling (`WaitTimeSeconds` ตั้งแต่ 1 ถึง 20 วินาที):** SQS จะรอจนกว่าจะมีข้อความเข้ามาในคิว หรือรอจนครบเวลาที่กำหนด โดยจะค้นหาข้ามทุกเซิร์ฟเวอร์ในคลัสเตอร์ **ช่วยกำจัดผลลัพธ์ว่างเปล่า ลดจำนวนคำขอ API และประหยัดค่าใช้จ่ายได้มหาศาล (Best Practice)**

### 2.4 Dead-Letter Queue (DLQ) และ Redrive Policy (สไลด์หน้า 24 & 35)
- **DLQ:** คิวพิเศษสำหรับพักข้อความที่มีปัญหา (Poison Pill Messages) ที่ประมวลผลไม่ผ่าน
- **Redrive Policy:** กำหนดค่า **`maxReceiveCount`** (เช่น ตั้งไว้ที่ 5 ครั้ง) หากข้อความใดถูกดึงไปรันแล้วล้มเหลวจนถูกเรียกซ้ำครบ 5 ครั้ง SQS จะย้ายข้อความนั้นไปเก็บไว้ใน DLQ อัตโนมัติ เพื่อให้วิศวกรมาตรวจสอบหาสาเหตุ โดยไม่ทำให้คิวหลักติดหล่ม
- **Message Retention Period:** ระยะเวลาที่ข้อความจะคงอยู่ในคิว ดีฟอลต์คือ **4 วัน** (ปรับได้ตั้งแต่ 1 นาที ถึง **14 วัน**)

## 3. Amazon SNS (Simple Notification Service)

บริการระบบกระจายข้อความแบบ Publish/Subscribe (Pub/Sub) สำหรับการส่งแบบ Many-to-Many:

### 3.1 รูปแบบปลายทางผู้รับ (Subscriber Endpoints)
1. **A2A (Application-to-Application):** **Amazon SQS Queues**, **AWS Lambda Functions**, Amazon Kinesis Data Firehose, HTTP/HTTPS Webhooks
2. **A2P (Application-to-Person):** อีเมล (Email), ข้อความสั้น (SMS), การแจ้งเตือนบนมือถือ (Mobile Push Notifications)

### 3.2 สถาปัตยกรรม Fanout Pattern (สไลด์หน้า 42)
- **รูปแบบ:** ผู้ส่ง (Publisher เช่น Ordering System) ยิงข้อความ `"new order"` เข้ามาที่ **SNS Topic** เพียงครั้งเดียว จากนั้น SNS Topic จะทำการ **โคลนและบรอดแคสต์ข้อความนั้นส่งต่อไปยัง SQS Queues หลายๆ คิวพร้อมกันแบบคู่ขนาน**
- **ตัวอย่างในสไลด์:**
  - คิวที่ 1: `Fulfillment SQS Queue` -> ส่งให้ EC2 จัดเตรียมสินค้า
  - คิวที่ 2: `Data Warehouse SQS Queue` -> ส่งให้ระบบบันทึกสถิติวิเคราะห์
  - คิวที่ 3: `Dev SQS Queue` -> ส่งให้ Lambda บันทึกลง Dev DynamoDB เพื่อทดสอบระบบ
- **ข้อดี:** ระบบงานแต่ละแผนกทำงานเป็นอิสระต่อกัน หากระบบวิเคราะห์ล่ม ระบบจัดส่งสินค้าก็ยังทำงานได้ปกติ

### 3.3 Message Filtering (การกรองข้อความที่ฝั่ง Subscriber - สไลด์หน้า 47-49)
- แต่เดิม Subscriber ทุกคนจะได้รับข้อความทุกชิ้นจาก Topic ทำให้ต้องเปลืองโค้ดมานั่ง Filter เอง
- **SNS Subscription Filter Policy:** กำหนดนโยบาย JSON ไว้ที่ตัว Subscription เช่น:
  ```json
  {
    "event_type": ["product_page_visited"]
  }
  ```
- เมื่อ Publisher ส่งข้อความพร้อมแนบ **`MessageAttributes`** ระบุ `'event_type': 'product_page_visited'` ทาง SNS จะส่งข้อความนี้ให้เฉพาะ Subscriber ที่มี Filter Policy ตรงกันเท่านั้น ช่วยลดภาระการประมวลผลของ Consumer ได้ 100%

## 4. Amazon Kinesis Data Streams (ระบบสตรีมข้อมูลความเร็วสูง)

- **Amazon Kinesis Data Streams:** บริการรับและจัดเก็บข้อมูลแบบสตรีมมิ่งต่อเนื่องขนาดใหญ่ระดับกิกะไบต์ต่อวินาที (เช่น Clickstreams, บันทึกการเล่นเกม, ข้อมูล IoT Sensors)
- **องค์ประกอบเชิงสถาปัตยกรรม:**
  - **Shards:** หน่วยย่อยของความจุใน Kinesis (1 Shard = รองรับการเขียน **1 MB/s หรือ 1,000 records/s**, รองรับการอ่าน **2 MB/s**)
  - **Data Retention:** ข้อมูลถูกเก็บไว้ในสตรีมได้ตั้งแต่ 24 ชั่วโมง ถึง 365 วัน (ดีฟอลต์ 24 ชม.)
  - **Shard Iterator:** ตัวชี้ตำแหน่งการอ่านข้อมูล เช่น `TRIM_HORIZON` (อ่านตั้งแต่ข้อมูลเก่าสุดที่มี) หรือ `LATEST` (อ่านเฉพาะข้อมูลใหม่ที่เพิ่งเข้ามา)
- **เครื่องมือพัฒนา (SDK & Libraries - สไลด์หน้า 61):**
  - **Kinesis Producer Library (KPL):** ไลบรารีสำหรับฝั่งเขียน ช่วยทำ Batching และ Retry อัตโนมัติเพื่อเร่ง Throughput สูงสุด
  - **Kinesis Client Library (KCL):** ไลบรารีสำหรับฝั่งอ่าน ช่วยจัดการโหลดบาลานซ์ข้ามเครื่อง และทำ Checkpointing จุดที่อ่านแล้วลงในตาราง DynamoDB อัตโนมัติ
- **บริการในตระกูล Kinesis:**
  - **Kinesis Data Firehose:** ส่งต่อข้อมูลจากสตรีมเข้าสู่ S3, Redshift, หรือ OpenSearch ได้โดยตรง **โดยไม่ต้องเขียนแอปพลิเคชัน Consumer เอง (Zero Code)**
  - **Kinesis Data Analytics:** รันคำสั่ง SQL หรือ Apache Flink กรองและวิเคราะห์ข้อมูลขณะที่กำลังลอยอยู่ในสตรีมแบบเรียลไทม์

## 5. ตารางเปรียบเทียบเชิงสถาปัตยกรรม (Comparison Tables)

### 5.1 Comparison: SQS Standard vs SQS FIFO

| มิติ | SQS Standard | SQS FIFO |
| :--- | :--- | :--- |
| **ลำดับข้อความ** | Best-effort (อาจสลับลำดับได้) | **Strictly Preserved (เข้าก่อนออกก่อน)** |
| **ข้อความซ้ำ** | มีโอกาสซ้ำได้ (At-least-once) | **ไม่มีซ้ำเด็ดขาด (Exactly-once)** |
| **Throughput** | ไม่จำกัด | 300 msg/s (สูงสุด 3,000 ด้วย Batch) |
| **Use Cases** | งานขนาดใหญ่ที่ไม่แคร์ลำดับ | ธุรกรรมการเงิน, การตัดสต็อกสินค้า |

### 5.2 Comparison: SQS Queues vs Kinesis Data Streams (สไลด์หน้า 62)

| คุณสมบัติ | Amazon SQS (คิว) | Amazon Kinesis Data Streams (สตรีม) |
| :--- | :--- | :--- |
| **คุณค่าของข้อมูล** | เกิดจากการประมวลผล **ข้อความเดี่ยวๆ แต่ละชิ้น** | เกิดจากการ **รวบรวมและวิเคราะห์ข้อมูลปริมาณมหาศาล (Aggregated Data)** |
| **อัตราการไหลของข้อมูล** | อัตราไม่แน่นอน แปรผันตามเวลา (Variable) | อัตราการไหล **ต่อเนื่องและปริมาณสูงตลอดเวลา (Continuous & High volume)** |
| **การจัดการข้อความหลังอ่าน** | **ข้อความถูกลบทิ้ง** เมื่อ Consumer ประมวลผลเสร็จ | **ข้อความยังคงอยู่ตาม Retention** Consumer ขยับแค่ Pointer ทำงานคู่ขนานได้หลายตัว |
| **ลำดับข้อมูล** | FIFO ทำได้ที่ความเร็วจำกัด | **รักษาลำดับข้อมูลภายใน Shard เดียวกันเสมอ** |

## 6. ⚠️ จุดหลอกและข้อควรระวังในห้องสอบ (Exam Traps & Pitfalls)

1. ❌ **หลอกเรื่องข้อความค้างใน SQS เพราะลืม DeleteMessage:** โจทย์ถามว่า Consumer ดึงข้อความมาประมวลผลสำเร็จแล้ว แต่ทำไมผ่านไป 30 วินาที ข้อความเดิมถึงถูกส่งไปให้ Consumer ตัวอื่นทำซ้ำอีกรอบ?
   - ✅ **ที่ถูกต้อง:** เพราะ Consumer **ไม่ได้ส่งคำสั่ง `DeleteMessage`** พร้อม `ReceiptHandle` กลับไปลบข้อความ เมื่อหมดเวลา Visibility Timeout ระบบ SQS จะมองว่าการทำงานล้มเหลวและปล่อยข้อความกลับเข้าคิว
2. ❌ **หลอกเรื่องการเลือกใช้ SQS Standard สำหรับธุรกรรมธนาคาร:** โจทย์ถามว่าระบบบันทึกยอดเงินฝาก-ถอนธนาคาร ต้องการส่งข้อความแบบอะซิงโครนัสโดยห้ามยอดติดลบและห้ามสลับลำดับ
   - ✅ **ที่ถูกต้อง:** **ต้องใช้ SQS FIFO เท่านั้น** ห้ามเลือก Standard Queue เพราะ Standard Queue ไม่การันตีลำดับและอาจมีข้อความซ้ำซ้อน ส่งผลให้ยอดเงินผิดพลาด
3. ❌ **หลอกเรื่องการตั้งเวลา Long Polling:** โจทย์ถามว่าต้องการลดต้นทุนค่าบริการ SQS และลดภาระ CPU ของเซิร์ฟเวอร์ที่คอยวนลูปถามคิวเปล่าๆ ควรปรับแต่งอย่างไร?
   - ✅ **ที่ถูกต้อง:** กำหนดค่า **`WaitTimeSeconds` ให้มากกว่า 0 (สูงสุด 20 วินาที)** ในคำสั่ง `ReceiveMessage` เพื่อเปิดใช้งาน **Long Polling**
4. ❌ **หลอกเรื่องการกระจายข้อความให้หลาย Consumer ด้วย SQS ตัวเดียว:** โจทย์ถามว่าต้องการให้ระบบ 3 ระบบที่ต่างกัน (เช่น จัดส่ง, บัญชี, แจ้งเตือน) ได้รับข้อความสั่งซื้อชุดเดียวกันทั้งหมด จึงต่อทั้ง 3 ระบบเข้ากับ SQS Queue เดียวกัน
   - ✅ **ที่ถูกต้อง:** ผิดหลักการ! เพราะข้อความใน SQS จะถูกดึงไปได้เพียง Consumer ตัวเดียวแล้วหายไป ทางแก้ที่ถูกต้องคือ **ใช้ SNS Topic ร่วมกับ Fanout Pattern ไปยัง 3 SQS Queues แยกกัน**
5. ❌ **หลอกเรื่องการส่งต่อข้อมูลเข้า S3 จาก Kinesis:** โจทย์ถามว่าต้องการนำข้อมูลจาก Kinesis Data Streams ไปเซฟลง S3 Bucket โดยไม่ต้องเขียนและดูแลแอปพลิเคชัน Consumer บน EC2/Lambda
   - ✅ **ที่ถูกต้อง:** ใช้ **Amazon Kinesis Data Firehose** ต่อจาก Kinesis Data Streams เข้าสู่ S3 ได้โดยตรงแบบไม่ต้องเขียนโค้ด

**สถานการณ์:** นักพัฒนากำลังออกแบบระบบประมวลผลธุรกรรมของธนาคารแบบอะซิงโครนัส ซึ่งประกอบด้วยรายการฝากและถอนเงิน โดยมีข้อกำหนดว่า **รายการธุรกรรมจะต้องถูกประมวลผลตามลำดับที่ส่งเข้ามาอย่างเคร่งครัด (In the order they arrive)** และห้ามเกิดการประมวลผลซ้ำซ้อนเด็ดขาด โซลูชันใดตอบสนองความต้องการนี้ได้ถูกต้อง?
- ก) ส่งข้อความธุรกรรมเข้าสู่ Amazon SQS Standard Queue
- ข) ส่งข้อความธุรกรรมเข้าสู่ Amazon Kinesis Data Streams
- ค) ส่งข้อความธุรกรรมเข้าสู่ Amazon SQS FIFO Queue
- ง) รัน Docker Containers บนคลัสเตอร์ Amazon ECS เพื่อดักจับข้อมูล
- **เฉลย:** **ค) ส่งข้อความธุรกรรมเข้าสู่ Amazon SQS FIFO Queue**
- **จุดหลอก (Exam Trap):** ข้อ ก (Standard Queue) ลำดับอาจคลาดเคลื่อนและมีโอกาสเกิดข้อความซ้ำ ส่วนข้อ ข (Kinesis) แม้จะเรียงลำดับใน Shard ได้ แต่ถูกออกแบบมาเพื่องานสตรีมมิ่งวิเคราะห์ข้อมูลรวม ไม่ใช่งานประมวลผลธุรกรรมเดี่ยวแบบธนาคาร
- **เหตุผลทางเทคนิค:** Amazon SQS FIFO Queue ออกแบบมาเพื่อรักษาระเบียบ First-In-First-Out 100% พร้อมฟังก์ชัน Exactly-once Processing จึงเป็นตัวเลือกที่สมบูรณ์แบบที่สุดสำหรับธุรกรรมการเงิน

### ข้อที่ 2: การออกแบบสถาปัตยกรรมกระจายข้อความแบบ Fanout ไปยังหลายระบบงาน
**สถานการณ์:** เว็บไซต์อีคอมเมิร์ซต้องการพัฒนาระบบเมื่อลูกค้าสั่งซื้อสินค้าสำเร็จ ข้อมูลการสั่งซื้อจะต้องถูกส่งไปประมวลผลพร้อมกันใน 3 แผนก ได้แก่ แผนกจัดเตรียมสินค้า, แผนกบัญชีออกใบกำกับภาษี, และแผนกสถิติการตลาด โดยแต่ละแผนกมีอัตราเร็วในการประมวลผลไม่เท่ากัน และหากแผนกใดแผนกหนึ่งหยุดทำงาน จะต้องไม่กระทบต่อแผนกอื่น สถาปัตยกรรมใดเหมาะสมที่สุด?
- ก) ให้หน้าเว็บส่งข้อความตรงไปยัง Amazon SQS Queue เดี่ยว แล้วให้ทั้ง 3 แผนกดึงข้อความแข่งกัน
- ข) ให้หน้าเว็บส่งข้อความเข้าสู่ Amazon SNS Topic จากนั้นสร้าง Amazon SQS Queue แยกสำหรับแต่ละแผนก แล้วนำคิวทั้ง 3 ไป Subscribe เข้ากับ SNS Topic ดังกล่าว
- ค) ให้หน้าเว็บยิงคำขอตรงไปยัง REST API ของทั้ง 3 แผนกพร้อมกันแบบ Synchronous
- ง) นำข้อมูลทั้งหมดไปบันทึกไว้ใน Amazon S3 แล้วตั้งเวลา Cron Job สแกนไฟล์ทุก 1 ชั่วโมง
- **เฉลย:** **ข) ให้หน้าเว็บส่งข้อความเข้าสู่ Amazon SNS Topic จากนั้นสร้าง Amazon SQS Queue แยกสำหรับแต่ละแผนก แล้วนำคิวทั้ง 3 ไป Subscribe เข้ากับ SNS Topic ดังกล่าว**
- **จุดหลอก (Exam Trap):** การใช้ SQS เดี่ยว (ข้อ ก) จะทำให้มีเพียงแผนกเดียวที่ได้ข้อความนั้นไป ส่วนข้อ ค เป็นการเชื่อมต่อแบบ Tight Coupling หากระบบใดช้าหน้าเว็บจะค้างตาม
- **เหตุผลทางเทคนิค:** นี่คือรูปแบบสถาปัตยกรรม **SNS Fanout to SQS Pattern** (สไลด์หน้า 42) ที่ช่วยคัดลอกข้อความกระจายไปยังคิวของแต่ละแผนกอย่างอิสระ มีบัฟเฟอร์แยกส่วน และทนทานต่อความผิดพลาดสูงสุด

### ข้อที่ 3: การลดค่าใช้จ่ายและกำจัดคำขอว่างเปล่าบน Amazon SQS
**สถานการณ์:** แอปพลิเคชันบน EC2 มีการเขียนโค้ดลูป `while True:` เพื่อเรียกฟังก์ชัน `ReceiveMessage` ตรวจสอบข้อความจาก SQS Queue ตลอดเวลา ผู้จัดการฝ่ายไอทีพบว่ามีค่าใช้จ่ายบิล AWS พุ่งสูงผิดปกติจากคำสั่ง ReceiveMessage ที่ส่งผลลัพธ์กลับมาเป็นข้อความว่างเปล่า (Empty Receives) นับล้านครั้งต่อวัน นักพัฒนาควรปรับปรุงโค้ดอย่างไรเพื่อลดค่าใช้จ่ายนี้?
- ก) เปลี่ยนไปใช้ FIFO Queue แทน Standard Queue
- ข) ปรับตั้งค่าพารามิเตอร์ `WaitTimeSeconds` เป็น 20 วินาที เพื่อเปิดใช้งาน Long Polling
- ค) ขยายเวลา Visibility Timeout ของคิวเป็น 12 ชั่วโมง
- ง) ติดตั้ง Auto Scaling Group เพื่อปิดเครื่อง EC2 เมื่อไม่มีงาน
- **เฉลย:** **ข) ปรับตั้งค่าพารามิเตอร์ `WaitTimeSeconds` เป็น 20 วินาที เพื่อเปิดใช้งาน Long Polling**
- **จุดหลอก (Exam Trap):** การปรับ Visibility Timeout (ข้อ ค) หรือเปลี่ยนชนิดคิว (ข้อ ก) ไม่ได้ช่วยลดความถี่ของคำขอวนลูปตรวจสอบข้อความ
- **เหตุผลทางเทคนิค:** การเปิดใช้งาน Long Polling โดยใส่ `WaitTimeSeconds` (1-20 วินาที) จะทำให้ SQS หน่วงเวลารอจนกว่าจะมีข้อความเข้ามาจริงจึงค่อยส่งผลลัพธ์กลับมา ช่วยลดจำนวนคำขอ API ที่ว่างเปล่าลงได้มหาศาล และลดค่าใช้จ่ายได้ทันที

### ข้อที่ 4: การจัดการกับข้อความที่เป็นพิษ (Poison Messages) ที่ประมวลผลไม่สำเร็จ
**สถานการณ์:** ในระบบประมวลผลคิว SQS มีข้อความชิ้นหนึ่งที่มีข้อมูลผิดรูปแบบ (Corrupted Data) ทำให้แอปพลิเคชันเกิดข้อผิดพลาดและแคชแครชทุกครั้งที่พยายามอ่านข้อความนี้ ส่งผลให้ข้อความดังกล่าววนกลับมาแสดงในคิวซ้ำไปซ้ำมาไม่รู้จบ และขัดขวางการทำงานของระบบ ควรแก้ไขปัญหานี้อย่างไรตามแนวทางของ AWS?
- ก) ตั้งค่า Redrive Policy บนคิว โดยกำหนด Dead-Letter Queue (DLQ) และตั้งค่า `maxReceiveCount` เป็น 3
- ข) ลดเวลา Message Retention Period ของคิวให้เหลือ 1 นาที
- ค) ปรับ Visibility Timeout ของคิวให้เป็น 0 วินาที
- ง) สั่งรันคำสั่ง PurgeQueue ทุกๆ 10 นาที
- **เฉลย:** **ก) ตั้งค่า Redrive Policy บนคิว โดยกำหนด Dead-Letter Queue (DLQ) และตั้งค่า `maxReceiveCount` เป็น 3**
- **จุดหลอก (Exam Trap):** การสั่ง PurgeQueue (ข้อ ง) หรือลด Retention เหลือ 1 นาที (ข้อ ข) จะทำให้ข้อความดีๆ ของลูกค้ารายอื่นถูกลบทิ้งไปด้วย
- **เหตุผลทางเทคนิค:** Dead-Letter Queue (DLQ) ร่วมกับ `maxReceiveCount` (สไลด์หน้า 24 & 35) ออกแบบมาเพื่อแยกข้อความที่ประมวลผลล้มเหลวซ้ำซากออกจากคิวหลักโดยอัตโนมัติ เพื่อให้ระบบสามารถประมวลผลข้อความอื่นต่อไปได้ และเก็บข้อความที่มีปัญหาไว้รอการดีบัก

### ข้อที่ 5: การส่งต่อข้อมูลสตรีมมิ่งลงสู่ S3 โดยไม่ต้องบริหารจัดการโค้ด
**สถานการณ์:** ฝ่ายวิเคราะห์ข้อมูลต้องการรวบรวมเหตุการณ์คลิกบนเว็บไซต์ (Clickstream Events) ปริมาณมหาศาลจาก Amazon Kinesis Data Streams แล้วนำไปจัดเก็บลงใน Amazon S3 ในรูปแบบไฟล์ Parquet เพื่อนำไปคิวรีต่อด้วย Amazon Athena ทีมงานต้องการโซลูชันแบบ Serverless ที่ไม่ต้องเขียน ไม่ต้องดีพลอย และไม่ต้องดูแลเซิร์ฟเวอร์ Consumer ใดๆ ควรเลือกบริการใด?
- ก) Amazon EMR Cluster ร่วมกับ Apache Spark Streaming
- ข) Amazon Kinesis Data Firehose
- ค) Amazon EC2 Instance ที่ติดตั้ง Kinesis Client Library (KCL)
- ง) AWS Glue ETL Job แบบตั้งเวลาทำงานรายวัน
- **เฉลย:** **ข) Amazon Kinesis Data Firehose**
- **จุดหลอก (Exam Trap):** ข้อ ก และ ค จำเป็นต้องเขียนโค้ดและบริหารจัดการเครื่องเซิร์ฟเวอร์ ส่วนข้อ ง ไม่ใช่การทำงานแบบสตรีมมิ่งเรียลไทม์
- **เหตุผลทางเทคนิค:** Amazon Kinesis Data Firehose (สไลด์หน้า 57) เป็นบริการแบบ Fully Managed ที่สามารถรับข้อมูลจาก Kinesis Data Streams แปลงฟอร์แมตข้อมูลเป็น Parquet/ORC และส่งมอบเข้าสู่ Amazon S3 ได้อัตโนมัติ โดยที่นักพัฒนาไม่ต้องเขียนโค้ดหรือดูแลระบบ Consumer เลยแม้แต่บรรทัดเดียว
