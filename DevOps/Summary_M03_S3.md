## 1. ภาพรวมและแก่นสำคัญ (Core Concept)

- **Amazon Simple Storage Service (Amazon S3):** เป็นบริการจัดเก็บข้อมูลประเภท **Object Storage** บนคลาวด์ ออกแบบมาเพื่อจัดเก็บและเรียกค้นข้อมูลปริมาณเท่าใดก็ได้จากทุกที่บนอินเทอร์เน็ต
- **ความทนทาน (Durability):** ออกแบบความทนทานของข้อมูลไว้สูงถึง **99.999999999% (11 9s)** ข้อมูลถูกจำลองกระจายข้ามหลาย Availability Zone (AZ) อัตโนมัติ
- **กรณีการใช้งานหลัก (Use Cases):**
  1. Content Storage and Distribution (จัดเก็บไฟล์มีเดียและกระจายเนื้อหา)
  2. Backup and Restore, and Archive (การสำรองข้อมูล กู้คืน และจัดเก็บระยะยาว)
  3. Data Lakes and Big Data Analytics (บ่อข้อมูลขนาดใหญ่สำหรับวิเคราะห์ข้อมูล)
  4. Disaster Recovery (DR - การกู้คืนระบบจากภัยพิบัติ)
  5. Static Website Hosting (โฮสต์เว็บไซต์สแตติก HTML, CSS, JS, รูปภาพ โดยไม่ต้องใช้เว็บเซิร์ฟเวอร์ EC2)

## 2. โครงสร้างและองค์ประกอบของ Amazon S3 (S3 Components)

### 2.1 Bucket (ถังจัดเก็บ)
- ถังเก็บข้อมูลระดับบนสุด อยู่ในระดับ **Regional** (ข้อมูลถูกเก็บในรีเจียนที่เลือกเพื่อจัดการ Latency, Cost, และ Compliance ทางกฎหมาย)
- **กฎการตั้งชื่อ Bucket (Bucket Naming Rules - ข้อสอบชอบออก):**
  - ชื่อต้อง **Globally Unique** ข้ามทุกบัญชี AWS ทั่วโลก
  - ความยาวระหว่าง **3 ถึง 63 ตัวอักษร**
  - อนุญาตเฉพาะ **ตัวพิมพ์เล็ก (lowercase), ตัวเลข (0-9), และเครื่องหมายขีดกลาง (-)** เท่านั้น
  - ❌ **ห้าม** มีตัวพิมพ์ใหญ่ (Uppercase) เด็ดขาด
  - ❌ **ห้าม** ใช้เครื่องหมาย Underscore (`_`)
  - ❌ **ห้าม** เริ่มต้นหรือลงท้ายด้วยเครื่องหมายขีดกลาง

### 2.2 Object & Key (วัตถุและคีย์ระบุตำแหน่ง)
- **Object:** ข้อมูลที่จัดเก็บ ประกอบด้วย Data (Payload) และ Metadata
- **Object Key:** สตริงชื่อเฉพาะที่ใช้ระบุออบเจกต์ภายใน Bucket (เปรียบเสมือนชื่อไฟล์และพาธ)
- **Prefixes (โฟลเดอร์เสมือน):** S3 เป็นโครงสร้างแบบแบน (Flat Structure) ไม่มีโฟลเดอร์จริง แต่ใช้สัญลักษณ์ `/` ใน Key เพื่อจำลองเป็นโครงสร้างโฟลเดอร์ เช่น Key `2021/DOC-EXAMPLE-BUCKET/math/john.txt` จะมี Prefix คือ `2021/DOC-EXAMPLE-BUCKET/math` เมื่อทำ GET ด้วย Prefix จะดึงเฉพาะออบเจกต์ในหมวดนั้นได้

### 2.3 รูปแบบ URL ของ S3 (S3 URL Formats)
- **Virtual-host-style URL (รูปแบบมาตรฐาน):**
  - โครงสร้าง: `http://<bucket-name>.s3-<aws-region>.amazonaws.com/<object-key>`
  - ตัวอย่าง: `http://DOC-EXAMPLE-BUCKET.s3.eu-west-1.amazonaws.com/cat.jpg`
- **Static Website Hosting URL (เมื่อเปิดฟีเจอร์ Web Hosting):**
  - โครงสร้าง: `http://<bucket-name>.s3-website-<aws-region>.amazonaws.com`
  - ตัวอย่าง: `http://DOC-EXAMPLE-BUCKET.s3-website-eu-west-1.amazonaws.com`

## 3. การจัดการ Metadata และการทำงานกับ Object (Object Operations)

### 3.1 Object Metadata (ข้อมูลอธิบายออบเจกต์)
จัดเก็บในรูปแบบ Key-Value Pairs แบ่งเป็น 2 ชนิด:
1. **System-defined Metadata:** ระบบ S3 จัดการและควบคุมเอง เช่น วันที่สร้าง (Creation Date), ขนาดไฟล์ (Size), เวอร์ชั่น (Version ID) และมีบางส่วนที่ผู้ใช้กำหนดได้ เช่น Storage Class, Server-Side Encryption
2. **User-defined Metadata:** ผู้ใช้สร้างขึ้นเองเพื่อกำกับบริบทของไฟล์ โดย Key ต้องขึ้นต้นด้วยคำว่า `x-amz-meta-` เสมอ (เช่น `x-amz-meta-alt-name: hero-banner`)

### 3.2 การอัปโหลด (PUT Object)
- **Single PUT Upload:** ใช้อัปโหลดไฟล์เดียวทั้งก้อน ขนาดไฟล์สูงสุดสำหรับการทำ Single PUT คือ **ไม่เกิน 5 GB**
- **Multipart Upload (การอัปโหลดแบบแยกส่วน):**
  - แนะนำให้ใช้ (Recommended) เมื่อไฟล์มีขนาด **มากกว่า 100 MB**
  - **บังคับต้องใช้ (Must Use)** เมื่อไฟล์มีขนาด **มากกว่า 5 GB**
  - ข้อดี: อัปโหลดชิ้นส่วนไฟล์แบบขนาน (Parallel Uploading) เร่ง Throughput สูงสุด, สามารถ Resume เฉพาะพาร์ตที่หลุดได้โดยไม่ต้องเริ่มใหม่ตั้งแต่ต้น
  - ขนาดไฟล์สูงสุดของออบเจกต์เดี่ยวบน S3 คือ **5 TB**

ตัวอย่างโค้ด Python Boto3 ในการ PUT Object:
```python
import boto3

S3API = boto3.client("s3", region_name="us-east-1")
bucket_name = "samplebucket"
filename = "/resources/website/core.css"

S3API.upload_file(
    filename, 
    bucket_name, 
    "core.css", 
    ExtraArgs={'ContentType': "text/css", "CacheControl": "max-age=0"}
)
```

### 3.3 การดึงข้อมูล (GET Object & S3 Select)
- **GET Object:** ดึงข้อมูลทั้งออบเจกต์ หรือดึงเฉพาะช่วงไบต์ที่ต้องการ (Range Header / Byte-range GET)
- **S3 Select (จุดสำคัญจากไดอะแกรมหน้า 23):**
  - **Before (แบบเดิม):** แอปพลิเคชันต้องดาวน์โหลดไฟล์ทั้งก้อนข้าม Network แล้วมารันกรองข้อมูล (Filter) ภายในแอปพลิเคชันเอง เสียแบนด์วิดท์และเปลืองทรัพยากร Compute
  - **After (ใช้ S3 Select):** ใช้คำสั่ง SQL พื้นฐานเพื่อสั่งให้ S3 กรองข้อมูล ณ จุดจัดเก็บ (In-place Filtering) แล้วส่งเฉพาะ Record ที่ตรงเงื่อนไขกลับมา
  - **ผลลัพธ์เชิงประสิทธิภาพ:** ประมวลผลเร็วขึ้นสูงสุด **400% (4 เท่า)** และประหยัดค่าใช้จ่ายด้าน Data Transfer ลงได้สูงสุดถึง **80%**

## 4. กลไก Versioning และการลบข้อมูล (Deletion Mechanism)

### 4.1 คุณสมบัติของ S3 Versioning
- ป้องกันความผิดพลาดจากการเผลอลบ (Accidental Deletion) หรือ Application Failure
- ทุกออบเจกต์จะมี Version ID กำกับ
- ⚠️ **กฎสำคัญ:** เมื่อเปิดใช้งาน Versioning บน Bucket แล้ว **ไม่สามารถปิด (Disable) ได้** ทำได้เพียงการระงับชั่วคราว (**Suspend**) เท่านั้น
- รองรับการทำ S3 Object Locking เพื่อทำ WORM (Write Once, Read Many)

### 4.2 กลไกการลบข้อมูล (DELETE Object) เชิงลึก
1. **เมื่อปิด Versioning (Versioning Disabled):**
   - การสั่ง DELETE จะลบออบเจกต์นั้นออกจากดิสก์แบบ **ถาวรทันที (Permanently Deleted)** ไม่สามารถกู้คืนได้
2. **เมื่อเปิดใช้งาน Versioning (Versioning Enabled - แยก 2 รูปแบบ):**
   - **กรณีที่ 1: สั่ง DELETE โดยระบุแค่ Object Key (Soft Delete):**
     - S3 จะไม่ลบไฟล์จริง แต่จะสร้าง **Delete Marker** (มี Version ID ใหม่ของตัวเอง) วางทับไว้เป็นชั้นบนสุด (Latest Version)
     - เมื่อมีคนส่งคำสั่ง GET ธรรมดามา จะได้สถานะ **404 Not Found**
     - ข้อมูลเวอร์ชันเก่าทั้งหมดยังคงอยู่ครบ 100%
     - *การกู้คืน:* ให้สั่งลบตัว Delete Marker ทิ้ง เวอร์ชันก่อนหน้าจะกลับมาเป็น Latest Version ทันที
   - **กรณีที่ 2: สั่ง DELETE โดยระบุทั้ง Object Key และ Version ID (Permanent Hard Delete):**
     - S3 จะลบเฉพาะเวอร์ชันที่ระบุ ID นั้นทิ้งอย่างถาวรทันที ไม่มีการสร้าง Delete Marker
     - เวอร์ชันก่อนหน้านั้นจะกลายมาเป็น Current Version ทันที

## 5. ความปลอดภัย การเข้ารหัส และการควบคุมสิทธิ์ (Security & Access Control)

### 5.1 การเข้ารหัสข้อมูล (Data Encryption)
1. **Data in Transit (ระหว่างส่ง):** ป้องกันด้วย SSL/TLS ผ่านโปรโตคอล HTTPS หรือการเข้ารหัสฝั่งไคลเอนต์ก่อนส่ง (Client-Side Encryption)
2. **Data at Rest (ขณะจัดเก็บ):**
   - **Client-Side Encryption:** ไคลเอนต์เข้ารหัสไฟล์เองก่อนอัปโหลดขึ้น S3
   - **Server-Side Encryption (SSE - ให้ S3 เข้ารหัสให้):**
     - **SSE-S3:** จัดการคีย์เข้ารหัสด้วย Amazon S3 Managed Keys (AES-256) ฟรี ไม่มีค่าใช้จ่ายคีย์
     - **SSE-KMS:** จัดการคีย์ผ่าน AWS Key Management Service มีการเก็บ Audit Log บน CloudTrail และจัดการสิทธิ์คีย์แยกต่างหากได้
     - **SSE-C:** Customer-Provided Keys ผู้ใช้งานส่งคีย์เข้ารหัสมาพร้อมกับคำขอ API แต่ละครั้ง AWS จะไม่เก็บคีย์นี้ไว้

### 5.2 การควบคุมสิทธิ์การเข้าถึง (Access Management)
เปรียบเทียบตามโครงสร้างภาษาและตำแหน่งที่ผูก (จากไดอะแกรมหน้า 30):
- **Identity-based Policies (เขียนด้วย JSON):**
  - ผูกติดกับตัวตนในระบบ IAM เช่น IAM Users, Groups หรือ Roles
  - กำหนดสิทธิ์ว่าตัวตนนั้นสามารถทำอะไรกับ Resource ใดได้บ้าง
- **Resource-based Policies:**
  - ผูกติดกับตัวทรัพยากร S3 โดยตรง เพื่อกำหนดว่าใคร (Principal) เข้ามาทำอะไรได้
  - **Bucket Policy (เขียนด้วย JSON):** นโยบายระดับถัง นิยมใช้กำหนดสิทธิ์แบบละเอียด เช่น เปิดสิทธิ์ Public Read สำหรับเว็บสแตติก, บังคับใช้ HTTPS, หรือกำหนดสิทธิ์ข้ามบัญชี (Cross-account)
  - **Access Control Lists (ACLs - เขียนด้วย XML):** ระบบดั้งเดิม ควบคุมสิทธิ์พื้นฐานระดับ Object หรือ Bucket (แนะนำให้ปิด Object Ownership เพื่อความปลอดภัย)

ตัวอย่าง Bucket Policy (อนุญาต Public Read):
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::DOC-EXAMPLE-BUCKET/*"]
    }
  ]
}
```

### 5.3 Presigned URLs (URL ชั่วคราว)
- ใช้มอบสิทธิ์ให้บุคคลภายนอกทำการ **GET หรือ PUT** ออบเจกต์เฉพาะเจาะจง โดยไม่ต้องเปิดสิทธิ์หรือสร้างบัญชี IAM ให้
- ใช้สิทธิ์และ Credentials ของผู้สร้าง URL ในขณะนั้น
- มีอายุการใช้งานจำกัดตามวันเวลาที่กำหนด (หมดอายุสูงสุดได้ไม่เกิน **1 สัปดาห์ หรือ 7 วัน**)

### 5.4 Cross-Origin Resource Sharing (CORS)
- กลไกอนุญาตให้เว็บแอปพลิเคชันที่โหลดจากโดเมนหนึ่ง (เช่น `http://www.example.com`) สามารถเรียกขอไฟล์จาก Bucket บนโดเมน S3 (เช่น `website.s3.amazonaws.com`) ได้
- กำหนดค่าเป็น JSON Rule ประกอบด้วย `AllowedOrigins`, `AllowedMethods`, `AllowedHeaders`, และ `MaxAgeSeconds`

## 6. ตารางเปรียบเทียบเชิงสถาปัตยกรรม (Comparison Tables)

### 6.1 รูปแบบการอัปโหลด: Single PUT vs Multipart Upload

| คุณสมบัติ | Single PUT Upload | Multipart Upload |
| :--- | :--- | :--- |
| **ขนาดไฟล์ที่เหมาะสม** | น้อยกว่า 100 MB | มากกว่า 100 MB ขึ้นไป |
| **ขีดจำกัดขนาดสูงสุด** | **5 GB** | **5 TB** (ชิ้นส่วนละ 5 MB ถึง 5 GB) |
| **ข้อบังคับ** | ไม่บังคับ | **บังคับต้องใช้เมื่อไฟล์ > 5 GB** |
| **การทำงานขนาน (Parallel)** | ไม่รองรับ (ส่งเป็นสตรีมก้อนเดียว) | รองรับ (อัปโหลดหลายพาร์ตพร้อมกัน) |
| **ความทนทานต่อเน็ตหลุด** | หลุดแล้วต้องเริ่มอัปโหลดใหม่ตั้งแต่ 0% | เริ่มใหม่เฉพาะพาร์ตที่ล้มเหลว (Resume ได้) |

### 6.2 กลไกการเข้ารหัสข้อมูลขณะจัดเก็บ (Server-Side Encryption)

| รูปแบบ | ผู้ดูแลคีย์ (Key Management) | การบันทึก Audit Log | เหมาะกับกรณี |
| :--- | :--- | :--- | :--- |
| **SSE-S3** | Amazon S3 (AWS จัดการ 100%) | ไม่มี Log การใช้คีย์เฉพาะ | ข้อมูลทั่วไป ไม่ต้องการ Audit เข้มงวด |
| **SSE-KMS** | AWS KMS (ผู้ใช้คุมนโยบายคีย์ได้) | มี Log ละเอียดบน AWS CloudTrail | องค์กรที่ต้องการ Compliance & Audit |
| **SSE-C** | ผู้ใช้งานเก็บและส่งคีย์มาเองทุกคำขอ | ฝั่งไคลเอนต์ต้องจัดการเองทั้งหมด | กฎหมายบังคับห้ามฝากคีย์ไว้กับ Cloud |

## 7. ⚠️ จุดหลอกและข้อควรระวังในห้องสอบ (Exam Traps & Pitfalls)

1. ❌ **หลอกเรื่องการปิด Versioning:** ข้อสอบมักถามว่า "หากต้องการยกเลิกการเก็บประวัติไฟล์ใน S3 Bucket ต้องกด Disable ใช่หรือไม่?"
   - ✅ **ที่ถูกต้อง:** S3 ไม่มีปุ่ม Disable ทำได้แค่ **Suspend (ระงับ)** เท่านั้น และไฟล์เวอร์ชันเก่าที่มีอยู่เดิมจะไม่ถูกลบ
2. ❌ **หลอกเรื่องขนาดไฟล์ Single Upload:** โจทย์มักถามว่าแอปพลิเคชันพยายามอัปโหลดไฟล์ขนาด 8 GB ด้วยคำสั่ง PUT ธรรมดาครั้งเดียว ทำไมถึงล้มเหลว?
   - ✅ **ที่ถูกต้อง:** คำสั่ง Single PUT รองรับได้สูงสุดเพียง **5 GB** หากเกิน 5 GB **ต้อง (Must)** ใช้ Multipart Upload
3. ❌ **หลอกเรื่องการลบใน Versioned Bucket:** โจทย์ถามว่า "สั่ง DELETE ไฟล์ `report.pdf` ไปแล้ว แต่ทำไมพื้นที่จัดเก็บและบิลค่ายังไม่ลดลง?"
   - ✅ **ที่ถูกต้อง:** หากสั่ง DELETE โดยไม่ระบุ Version ID ระบบจะสร้างแค่ **Delete Marker** ทับไว้ เนื้อไฟล์จริงยังอยู่ครบทุกเวอร์ชัน ต้องสั่งลบแบบระบุ Version ID หรือตั้ง Lifecycle Rule ให้กวาดลบ Noncurrent Versions จึงจะคืนพื้นที่จริง
4. ❌ **หลอกเรื่อง Presigned URL Expiration:** โจทย์ถามว่าสามารถสร้าง Presigned URL ที่ไม่มีวันหมดอายุ หรือมีอายุ 1 เดือนได้หรือไม่?
   - ✅ **ที่ถูกต้อง:** Presigned URL มีอายุขัยสูงสุดได้ไม่เกิน **7 วัน (1 สัปดาห์)**
5. ❌ **หลอกเรื่องชื่อ Bucket:** โจทย์ให้เลือกชื่อ Bucket ที่ถูกต้อง มีตัวพิมพ์ใหญ่ เช่น `My-Company-Data` หรือมี Underscore `my_company_data`
   - ✅ **ที่ถูกต้อง:** ทั้งสองชื่อผิดกฎ ชื่อต้องเป็นตัวพิมพ์เล็กและห้ามมี Underscore

## 8. 📝 คลังข้อสอบจำลองสถานการณ์จริง (Scenario-Based Exam Simulation)

### ข้อที่ 1: การป้องกันความผิดพลาดจากการลบข้อมูล (AWS Academy Slide 43-45)
**สถานการณ์:** ทีมขายของบริษัทต้องอัปโหลดเอกสารสรุปยอดขายเข้าสู่ระบบทุกวัน ฝ่ายพัฒนาระบบต้องการพื้นที่จัดเก็บข้อมูลที่มีความทนทานสูง และต้องการป้องกันไม่ให้พนักงานเผลอกดลบเอกสารสำคัญโดยไม่ตั้งใจ ควรเลือกแนวทางใด?
- ก) จัดเก็บข้อมูลบน Amazon EBS Volume และทำ Snapshot ทุกสัปดาห์
- ข) จัดเก็บข้อมูลบน Amazon S3 Bucket และเปิดใช้งาน Versioning
- ค) จัดเก็บข้อมูลบน Amazon S3 Bucket 2 ถังที่อยู่ต่าง AWS Regions กัน
- ง) จัดเก็บข้อมูลบน EC2 Instance Store
- **เฉลย:** **ข) จัดเก็บข้อมูลบน Amazon S3 Bucket และเปิดใช้งาน Versioning**
- **จุดหลอก (Exam Trap):** ข้อ ก และ ง เป็น Block storage/Ephemeral storage ที่ไม่ตรงตามโจทย์เรื่องความทนทานสูง ส่วนข้อ ค การข้าม Region ช่วยเรื่อง Disaster Recovery แต่ถ้าต้นทางเผลอลบ ปลายทางก็ถูกลบตามได้หากทำ Replication Sync
- **เหตุผลทางเทคนิค:** S3 มีความทนทาน 11 9s และการเปิด Versioning ทำให้เมื่อมีคำสั่งลบโดยไม่ตั้งใจ จะสร้างเพียง Delete Marker ผู้ดูแลสามารถกู้คืนไฟล์กลับมาได้เสมอ

### ข้อที่ 2: การอัปโหลดไฟล์ขนาดใหญ่
**สถานการณ์:** วิศวกรซอฟต์แวร์กำลังพัฒนาระบบแบ็กอัปไฟล์วิดีโอดิบขนาด 12 GB ขึ้นสู่ Amazon S3 ผ่านโค้ด Python แต่พบข้อผิดพลาดขณะส่งคำสั่ง PUT อัปโหลดไฟล์ วิศวกรควรปรับปรุงระบบอย่างไรจึงจะถูกต้องและมีประสิทธิภาพสูงสุด?
- ก) ขยาย Timeout ของคำขอ HTTP PUT เป็น 60 นาที
- ข) เข้ารหัสไฟล์ด้วย SSE-C ก่อนทำการอัปโหลดแบบ Single PUT
- ค) เปลี่ยนไปใช้ Multipart Upload API เพื่อแยกไฟล์และอัปโหลดแบบคู่ขนาน
- ง) บีบอัดไฟล์วิดีโอให้เหลือขนาดต่ำกว่า 10 GB แล้วอัปโหลดด้วยคำสั่ง PUT เดิม
- **เฉลย:** **ค) เปลี่ยนไปใช้ Multipart Upload API เพื่อแยกไฟล์และอัปโหลดแบบคู่ขนาน**
- **จุดหลอก (Exam Trap):** ข้อสอบมักลวงด้วยการปรับ Parameter ของคำขอ (เช่น ปรับ Timeout) แต่ข้อจำกัดทางสถาปัตยกรรมของ S3 Single PUT ถูกฮาร์ดลิมิตไว้ที่ 5 GB ไฟล์ 12 GB จึงไม่มีทางส่งผ่านได้
- **เหตุผลทางเทคนิค:** ไฟล์ที่เกิน 5 GB ถูกบังคับให้ต้องใช้ Multipart Upload นอกจากนี้การแบ่งชิ้นส่วนยังช่วยให้อัปโหลดแบบคู่ขนาน เร่งสปีด และสามารถกู้คืนเฉพาะพาร์ตที่หลุดได้

### ข้อที่ 3: การเพิ่มความเร็วและลดต้นทุนในการดึงข้อมูลจากไฟล์ขนาดใหญ่
**สถานการณ์:** แอปพลิเคชันประมวลผลข้อมูลต้องดึงไฟล์ CSV ขนาด 20 GB จาก S3 ทุกชั่วโมง เพื่อนำมาอ่านเฉพาะแถวข้อมูลของลูกค้าในประเทศไทย (ประมาณ 50 MB) จากนั้นนำมาคำนวณ พบว่าแอปพลิเคชันทำงานช้าและเสียค่าใช้จ่าย Data Transfer สูงมาก ควรใช้บริการหรือฟีเจอร์ใดของ S3 เพื่อแก้ปัญหานี้โดยตรง?
- ก) S3 Transfer Acceleration
- ข) S3 Select
- ค) S3 Glacier Flexible Retrieval
- ง) Amazon CloudFront Caching
- **เฉลย:** **ข) S3 Select**
- **จุดหลอก (Exam Trap):** หลายคนมักสับสนกับ Transfer Acceleration ซึ่งใช้สำหรับเร่งความเร็วการอัปโหลดผ่าน CloudFront Edge ไม่ได้ช่วยกรองข้อมูล และ CloudFront Caching ก็ยังคงแคชไฟล์ 20 GB ทั้งก้อน
- **เหตุผลทางเทคนิค:** S3 Select ช่วยให้สามารถใช้คำสั่ง SQL กรองเฉพาะข้อมูลที่ต้องการได้จากฝั่ง S3 Storage โดยตรง ลดปริมาณข้อมูลที่ต้องส่งผ่านเครือข่ายลงได้สูงสุด 80-99% และเพิ่มความเร็วได้สูงสุด 400%

### ข้อที่ 4: การแชร์ไฟล์ให้ลูกค้าภายนอกอย่างปลอดภัยโดยไม่เปิด Public
**สถานการณ์:** บริษัทที่ปรึกษาการเงินต้องการส่งรายงานผลการวิเคราะห์ในรูปแบบ PDF ให้ลูกค้าดาวน์โหลด ลูกค้าไม่มีบัญชี AWS และบริษัทมีนโยบายห้ามเปิดสิทธิ์ Public บน S3 Bucket เด็ดขาด รวมถึงต้องการให้ลิงก์ดาวน์โหลดหมดอายุภายใน 24 ชั่วโมง สถาปัตยกรรมใดเหมาะสมที่สุด?
- ก) สร้าง IAM User ใหม่ให้ลูกค้าพร้อมแนบ Policy จำกัดสิทธิ์
- ข) สร้าง Presigned URL สำหรับไฟล์ PDF โดยตั้งค่า Expiration ไว้ที่ 24 ชั่วโมง
- ค) ปรับแก้ Bucket Policy ให้ใส่เงื่อนไข IP Address ของลูกค้า
- ง) สร้าง Bucket ACL แบบ XML ให้สิทธิ์ Read แก่ anonymous user
- **เฉลย:** **ข) สร้าง Presigned URL สำหรับไฟล์ PDF โดยตั้งค่า Expiration ไว้ที่ 24 ชั่วโมง**
- **จุดหลอก (Exam Trap):** การสร้าง IAM User ให้ลูกค้าภายนอกเป็นการสิ้นเปลืองและเสี่ยงต่อความปลอดภัย ส่วนการใส่ IP บน Bucket Policy หรือเปิด ACL เป็นการเปิดช่องโหว่และยุ่งยากในการดูแล
- **เหตุผลทางเทคนิค:** Presigned URL สร้างขึ้นมาเพื่อกรณีนี้โดยเฉพาะ อนุญาตให้ไคลเอนต์ภายนอกดาวน์โหลดไฟล์ผ่าน URL ที่มี Security Token ชั่วคราว โดยกำหนดอายุได้สูงสุด 7 วัน

### ข้อที่ 5: พฤติกรรมของ S3 Versioning เมื่อถูกลบ
**สถานการณ์:** ถังข้อมูล `contracts-bucket` เปิดใช้งาน Versioning อยู่ ภายในมีไฟล์ `contract.pdf` โดยมี Version ID ล่าสุดคือ `v2` และเวอร์ชันเดิมคือ `v1` หากผู้ดูแลระบบส่งคำสั่ง `DELETE s3://contracts-bucket/contract.pdf` โดยไม่ได้ระบุ Version ID จะเกิดผลลัพธ์ใดตามลำดับ?
- ก) ไฟล์ `v2` ถูกลบถาวรทันที และ `v1` จะกลายเป็น Current Version
- ข) ไฟล์ทั้ง `v1` และ `v2` จะถูกย้ายไปอยู่ในถังขยะ S3 Trash
- ค) S3 จะสร้าง Delete Marker ขึ้นมาเป็น Current Version และคำสั่ง GET ธรรมดาจะได้รับผลลัพธ์ 404
- ง) คำขอจะถูกปฏิเสธ (403 Access Denied) เนื่องจากเปิด Versioning อยู่ ห้ามลบหากไม่ระบุ Version ID
- **เฉลย:** **ค) S3 จะสร้าง Delete Marker ขึ้นมาเป็น Current Version และคำสั่ง GET ธรรมดาจะได้รับผลลัพธ์ 404**
- **จุดหลอก (Exam Trap):** คนส่วนใหญ่คิดว่าถ้าไม่ระบุ Version ID ระบบจะลบเวอร์ชันล่าสุดทิ้งไป แต่ความเป็นจริงคือระบบจะไม่ลบไฟล์ใดๆ เลย แต่จะสร้าง Delete Marker สวมทับไว้ด้านบน
- **เหตุผลทางเทคนิค:** ในถังที่เปิด Versioning การส่งคำสั่ง DELETE ด้วย Key เพียงอย่างเดียวคือการทำ Soft Delete โดยการวาง Delete Marker ทับ หากต้องการลบถาวร ต้องระบุ Version ID ในคำสั่ง DELETE เสมอ
